# Appointment-request processing belongs to a project plugin

The theme owns presentation; a small project-owned plugin owns appointment-request processing so changing themes preserves business functionality. This establishes the exception allowed by the WordPress runtime boundary without introducing a third-party form dependency. The later content-model decision in ADR 0004 approves exactly Service and Project custom post types; this processing boundary does not authorize additional types.

Delivery is email-only for this pilot, with no customer-submission storage or request-management system in WordPress. This accepts the absence of a durable WordPress recovery copy in return for a smaller lead-generation implementation. Acceptance requires local mail capture and a real delivery check; a successful mail API result alone is not proof of inbox receipt.

The plugin sends one studio notification through `wp_mail()` using a separately configured administrative recipient, a site-controlled sender, and the customer's validated optional email as Reply-To. There is no automatic customer email. Missing configuration or a transport failure cannot render success, and success communicates acceptance for sending rather than a confirmed appointment. Environment-specific mail transport and credentials remain outside repository source.

Anonymous requests start with a honeypot, WordPress request/CSRF protection, and privacy-conscious short-lived server-side throttling, without CAPTCHA or an external anti-spam dependency. An anonymous token is not a durable identity or sole throttle key; clearing its cookie must not entirely bypass throttling. Abuse state must be explicitly bounded and must not retain raw personal form fields. Any future caching must preserve correct form/token/error behavior without unnecessarily disabling unrelated-page caching.

The project plugin is a required runtime dependency for the completed product. Its absence is a production acceptance failure: the theme must avoid fatal errors, submission must fail closed without a false success path, a reasonable public contact fallback should appear where possible, and administrators must receive a clear diagnostic notice. Degraded behavior is a failure safeguard, not a supported normal operating mode.
