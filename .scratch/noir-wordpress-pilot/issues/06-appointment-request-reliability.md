# 06: Harden Appointment Request against replay, concurrency and uncertain delivery

**What to build:** Customers receive safe, honest outcomes when requests are repeated, concurrent, expired, throttled or uncertain. One request token cannot cause multiple sends, and concurrent duplicate submissions produce at most one transport attempt. Complete the approved bounded, privacy-conscious reliability contract using the smallest maintainable project-specific implementation.

**Blocked by:** 05 — Submit a validated Appointment Request end-to-end.

**Status:** ready-for-agent

- [ ] Short-lived throttling limits submissions and token issuance, remains effective under concurrent requests and cookie clearing, and prevents unbounded abuse-state growth. Honor forwarded addresses only for explicitly trusted proxies. Persist only scoped keyed digests and necessary operational counters/timestamps, never customer fields, raw IPs, mail payloads or request bodies. Document simple pilot-appropriate limits/windows; throttled responses use 429 and Retry-After.
- [ ] One token cannot cause multiple sends; simultaneous valid POSTs using that token invoke transport at most once. Establish exclusive permission across independent workers using the smallest supported WordPress solution that proves the property. No database engine, custom table, SQL claim or locking design is mandated. Fail closed before sending if required safeguards or storage cannot reliably establish exclusivity.
- [ ] Concurrent/replayed in-progress submissions never initiate another transport attempt. Accepted replay returns the existing authenticated accepted outcome while available and never resends. Invalid, missing or expired tokens fail safely and cannot create issuance state through POST. Proven non-acceptance permits only a later explicit safe retry; uncertainty never does.
- [ ] Timeouts, crashes, ambiguous transport errors and post-send acceptance-recording failure produce a pending/uncertain non-success response with direct-contact guidance, never automatic retry. No timeout, expiry or cleanup can authorize a competing attempt while the original could still send. Success requires attributable recorded transport acceptance; exactly-once email delivery is not promised.
- [ ] Temporary token/replay/uncertainty and throttle state has documented finite retention, a simple growth bound and effective cleanup. Choose and justify short lifetimes, any pending threshold and cleanup method for the actual implementation. No fixed row capacities, cleanup batch size, hourly scheduling or 30-minute/24-hour/120-second values are required. Expiry or removal of protective state makes the old token invalid; it cannot reopen sending. Refuse new work when correctness cannot be preserved.
- [ ] Contact/form/status and error responses are no-store; shared caching cannot mix visitor tokens or receipts. Other pages remain cacheable. Prove isolation without adding a speculative caching or token-refresh platform.
- [ ] Focused real WordPress tests use independent concurrent HTTP requests/workers and the chosen storage to prove duplicate exclusion, accepted replay, concurrent abuse protection, safe invalid/expired tokens, bounded state growth and actual cleanup. Cover cookie clearing, forged proxy headers, storage failures, definite versus uncertain transport outcomes, interrupted/slow workers and post-send recording failure, including accessible no-JavaScript outcomes. Sequential replay alone does not prove concurrency safety.
- [ ] Keep all hardening specific to this pilot and reuse Ticket 05's request path. Do not introduce a generic queue, messaging system, workflow engine, extension framework or reusable distributed-systems infrastructure.
